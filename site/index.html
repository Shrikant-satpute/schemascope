The difference

Minutes of waiting, replaced by one second.

Visual Studio's Schema Compare builds a full model of both databases before it can tell you anything, and it only ever does one pair at a time. SchemaScope reads the system catalog instead — two round trips per database — then hashes every object. Measured on a real 1,189 object database against a 990 object copy.

Why not just use Visual Studio?

Schema Compare sucks at this job.

It is fine at what it was built for — pushing one database into another. Ask it the question people actually ask on a Friday afternoon, is production still the same as dev?, and it wastes your afternoon. Anyone who has sat watching that progress bar knows exactly why.

Slow. Every single time.

Before it says one word, it builds a full model of both databases. On a large database that is minutes of watching a progress bar — and you pay it again on every run.

One pair at a time. That is it.

Four environments means running it four times, waiting four times, and then holding four sets of results in your head.

It cries wolf.

Re-indent a stored procedure and it screams "changed". The one difference that will actually break production is buried in that noise.

It drags a whole IDE along.

A DBA who does not write C# should not have to install a multi-gigabyte IDE to find out whether last night's release landed.

Six answers, not two

A re-indented procedure is not a change.

Most tools say "same" or "different" — which reports reformatted code as drift and buries the differences that matter. SchemaScope separates them, and never hides anything: an ignore rule moves an object down a level rather than making it disappear.

=

Same

Identical to the source. Settled by hash, never looked at again.

~

Formatting

Same code. Only spacing, comments or brackets moved.

≠

Different

A real difference, with the number of changed lines beside it.

✕

Missing

In the source, but not in this target. A release that did not land.

+

Extra

Only in this target. Usually somebody's local change.

?

Unreadable

Encrypted, or your login lacks VIEW DEFINITION. Said plainly, never guessed.

Privacy

Enforced, not promised.

SchemaScope is for people whose schema is not allowed to leave the building. Every one of these is a mechanism you can check in the source, not a policy in a document.

The browser engine blocks the network for us.

The UI runs under Content-Security-Policy: default-src 'self'. A request to an outside host is not refused by our code — it is refused before it is made.

Passwords are encrypted with Windows DPAPI.

Scoped to your Windows account. Another user on the same PC cannot read them even holding the database file.

No telemetry. No update check. No network calls at all.

Not "anonymised analytics" — none. The only connections SchemaScope opens are to the databases you named.

Read-only, structurally.

There is no code path in SchemaScope that writes to a database. It produces scripts and reports; applying them stays your decision, in your own tools.

Installing

Two clicks to a desktop icon.

Download the installer

About 30 MB. Everything is bundled — no .NET install, nothing to unpack.

Run it

Installs for your account only, so Windows never asks for administrator rights. Tick the box for a desktop shortcut.

Point it at your databases

Add one source and as many targets as you like. A login with VIEW DEFINITION is all it needs.

Windows will warn you on first run

SchemaScope is not code-signed yet, so SmartScreen shows "Windows protected your PC". Click More info, then Run anyway. A signing certificate is on the roadmap.

You do not have to take that on trust. Every release is built in public by GitHub Actions from a tagged commit, and ships a SHA256SUMS.txt you can check:

Get-FileHash .\SchemaScope-Setup.exe -Algorithm SHA256
